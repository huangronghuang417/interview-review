第一梯队：必考（99%会问到）
Q1：Buffer Pool 是干什么的？为什么 MySQL 需要它？

Buffer Pool 是 InnoDB 的内存缓冲池，用于缓存数据页和索引页（默认 128MB，生产环境通常设物理内存的 50%~75%）。

为什么需要：磁盘 IO 是毫秒级，内存是纳秒级，差了几万倍。如果每次读写都直接操作磁盘，数据库根本扛不住并发。Buffer Pool 把热点数据页缓存在内存中，读数据时先查 Buffer Pool（命中就直接返回），写数据时先改 Buffer Pool 中的页（产生脏页），再靠 redo log 和后台线程异步刷盘。所有 SQL 的读写操作都经过 Buffer Pool。

Q2：Buffer Pool 里有哪些链表？各自干什么？

核心三条链表：

Free List（空闲链表）：记录哪些缓存页是空的，需要加载新数据页时从 Free List 取。
LRU List（最近最少使用链表）：管理已被使用的缓存页，按访问热度排序。需要淘汰页时从尾部淘汰。InnoDB 对 LRU 做了优化——分为 young 区（新页区，占 5/8）和 old 区（旧页区，占 3/8），新加载的页先放 old 区头部，只有被再次访问后才晋升到 young 区，防止全表扫描一次性污染整个 Buffer Pool。
Flush List（刷盘链表）：管理所有脏页，按修改时间（LSN）排序，后台线程从 Flush List 尾部取脏页刷盘。
Q3：Change Buffer 是什么？解决了什么问题？

Change Buffer 是 Buffer Pool 中的一块特殊区域，用于缓存非唯一索引上不在 Buffer Pool 中的数据页的 INSERT/UPDATE/DELETE 操作。

解决的问题：如果一条 UPDATE 要修改的非唯一索引页不在 Buffer Pool 中，传统做法必须把索引页从磁盘加载到内存再修改（一次随机 IO）。有了 Change Buffer，可以先不加载索引页，而是把修改操作缓存到 Change Buffer 中，等后续查询需要访问该索引页时再合并（merge）到索引页中。这样把多次随机 IO 合并为一次，大幅减少磁盘 IO，提升写性能。

限制：

只适用于非唯一索引（唯一索引需要立即检查唯一性约束，必须加载索引页）
只缓存不在 Buffer Pool 中的索引页的修改
事务提交时 Change Buffer 的修改会写入 redo log（保证崩溃恢复）
Q4：Log Buffer 是什么？什么时候刷盘？

Log Buffer 是 redo log 的用户空间缓冲区，事务执行过程中产生的 redo log 先写到这里，然后批量写入 OS Cache 和磁盘。

刷盘时机（由 innodb_flush_log_at_trx_commit 控制）：

事务提交时（参数=1 则 fsync 到磁盘）
每秒一次（后台线程）
Log Buffer 使用超过一半时

为什么需要 Log Buffer：如果每次产生一条 redo log 就直接 fsync，高并发下 IO 次数爆炸。Log Buffer 让多个事务的 redo log 可以批量写入，配合组提交（group commit）大幅减少 fsync 次数。

Q5：Buffer Pool 的 LRU 算法和普通 LRU 有什么区别？为什么这么设计？

普通 LRU：新访问的页放头部，满了从尾部淘汰。

InnoDB LRU 的问题：如果执行全表扫描（SELECT * FROM 大表），会把整个 Buffer Pool 的热数据全部挤出去，导致后续正常查询大量缺页，性能骤降。

InnoDB 的改进：把 LRU List 分成两部分：

young 区（新页区）：占 5/8，存放真正的热点数据
old 区（旧页区）：占 3/8，存放新加载但还没被二次访问的页

新页加载策略：数据页首次加载时，放在 old 区的头部，而不是 young 区。只有该页在 old 区被再次访问（且两次访问间隔超过 innodb_old_blocks_time，默认 1 秒），才会晋升到 young 区头部。

效果：全表扫描时，大量页被加载到 old 区头部，但只被访问一次，不会晋升到 young 区，因此不会污染热点数据。扫描结束后这些页自然从 old 区尾部淘汰。

第二梯队：高频（70%+会问）
Q6：脏页是怎么产生的？什么时候刷盘？

产生：事务修改 Buffer Pool 中的数据页后，该页变成脏页（内存与磁盘不一致）。

刷盘时机：

后台线程定期刷（page cleaner thread，每秒/每10秒）
Buffer Pool 内存不足，需要空闲页时淘汰脏页（先刷盘再释放）
redo log 写满，需要覆盖旧日志时强制刷盘（checkpoint 推进）
数据库正常关闭时全量刷盘
Q7：自适应哈希索引（AHI）是什么？

InnoDB 会自动监控某些索引值的访问模式，如果发现某个索引页被频繁等值查询（如 WHERE id = xxx），会在内存中为该索引页建立哈希索引，将 B+ 树查找（O(log n)）优化为哈希查找（O(1)）。

特点：

完全自动，无需人工干预
只适用于等值查询，范围查询无效
只针对热点数据页
可通过 innodb_adaptive_hash_index 关闭（某些高并发场景关闭反而减少锁竞争）
Q8：Sort Buffer 和 Join Buffer 是什么？跟 Buffer Pool 什么关系？

Sort Buffer：每个会话独占的内存区域，用于 ORDER BY 排序操作。如果排序数据量超过 sort_buffer_size，则使用磁盘临时文件做外部排序。

Join Buffer：每个会话独占的内存区域，用于非索引驱动表的 Block Nested-Loop Join。将驱动表的数据批量加载到 Join Buffer，然后跟被驱动表逐行比对，减少磁盘 IO。

跟 Buffer Pool 的关系：Sort Buffer 和 Join Buffer 是会话级内存，不经过 Buffer Pool，由 MySQL Server 层分配。Buffer Pool 是 InnoDB 引擎层的全局共享内存。两者独立。

Q9：如何监控 Buffer Pool 的使用情况？命中率怎么看？
sql
SHOW ENGINE INNODB STATUS;

看 BUFFER POOL AND MEMORY 段：

Buffer pool hit rate：命中率（正常应 > 99%）
Pages read / Pages created / Pages written：读写统计
Youngs/s / Non-youngs/s：young 区/old 区的访问频率

命中率低于 95% 说明 Buffer Pool 太小或全表扫描太频繁。

Q10：Buffer Pool 设置多大合适？太大有什么问题？

建议：物理内存的 50%~75%，专用数据库服务器可以设到 80%。

不能太大：

操作系统需要内存做文件系统缓存（page cache），如果 Buffer Pool 占满所有内存，OS Cache 不足，会影响 binlog、redo log 的写入性能
内存越大，InnoDB 后台线程扫描 LRU/Flush List 的开销越大
极端情况下可能触发 OOM
第三梯队：中频（偶尔会问）
Q11：预读（Read-Ahead）是什么？

InnoDB 会预测接下来可能需要的数据页，提前异步加载到 Buffer Pool 中。

线性预读：顺序扫描超过 innodb_read_ahead_threshold（默认 56）个页时，触发预读下一个 extent（64个页）
随机预读：一个 extent 中有 13 个页被加载到 Buffer Pool 时，触发预读该 extent 剩余页
预读可以减少后续查询的磁盘 IO 等待。
Q12：Doublewrite Buffer 是什么？为什么需要它？

Doublewrite Buffer 是内存中 2MB 的缓冲区 + 磁盘上 2MB 的连续区域（128个页）。

解决的问题：脏页刷盘时，如果写到一半（比如写了 4KB 的页只写了 2KB）发生崩溃，数据页就损坏了。redo log 只能恢复"逻辑修改"，不能修复"页本身损坏"（因为不知道原来的值是什么）。

流程：脏页刷盘时，先写入 Doublewrite Buffer（内存→磁盘连续区域，顺序写），然后再写入真正的数据文件（随机写）。崩溃恢复时，如果数据页损坏，可以从 Doublewrite Buffer 的副本中恢复完整页，再用 redo log 重放修改。  
  
REDIS
一 认识redis
Q1 ：什么是redis    

Redis 是⼀种基于内存的数据库，对数据的读写操作都是在内存中完成，因此读写速度⾮常
快，常⽤于缓存，消息队列、分布式锁等场景。  
  

Redis 提供了多种数据类型来⽀持不同的业务场景，⽐如 String(字符串)、Hash(哈希)、
List (列表)、Set(集合)、Zset(有序集合)、Bitmaps（位图）、HyperLogLog（基数统计）、
GEO（地理信息）、Stream（流），并且对数据类型的操作都是原⼦性的，因为执⾏命令
由单线程负责的，不存在并发竞争的问题。  

除此之外，Redis 还⽀持事务 、持久化、Lua 脚本、多种集群⽅案（主从复制模式、哨兵模
式、切⽚机群模式）、发布/订阅模式，内存淘汰机制、过期删除机制等等。
  
Q2   Redis 和 Memcached 有什么区别？
Redis 与 Memcached 共同点：
1. 都是基于内存的数据库，⼀般都⽤来当做缓存使⽤。
2. 都有过期策略。
3. 两者的性能都⾮常⾼。  

**Redis 与 Memcached 区别：**  
  

   Redis ⽀持的数据类型更丰富（String、Hash、List、Set、ZSet），⽽
   Memcached 只⽀持最简单的 key-value 数据类型；  

   Redis ⽀持数据的持久化，可以将内存中的数据保持在磁盘中，重启的时候可以再
   次加载进⾏使⽤，⽽ Memcached 没有持久化功能，数据全部存在内存之中，
   Memcached 重启或者挂掉后，数据就没了；  

   Redis 原⽣⽀持集群模式，Memcached 没有原⽣的集群模式，需要依靠客户端来
   实现往集群中分⽚写⼊数据；  

   Redis ⽀持发布订阅模型、Lua 脚本、事务等功能，⽽ Memcached 不⽀持；   
     
Q3：为什么用 Redis 作为 MySQL 的缓存？  
主要是因为 Redis 具备「⾼性能」和「⾼并发」两种特性。  
1. 高性能（读写速度快）

MySQL 是磁盘数据库，数据存储在硬盘上，读写涉及磁盘 I/O，延迟较高（毫秒级）。  

Redis 是内存数据库，所有数据读写都在内存中完成，速度极快（纳秒~微秒级）。  

将热点数据缓存到 Redis 中，后续请求直接从内存读取，避免频繁访问 MySQL，响应时间从毫秒级降到微秒级。  

2. 高并发（支撑更高 QPS）

Redis 单机的 QPS（每秒查询率）轻松突破 10 万，而 MySQL 单机很难破 1 万。  

在高并发场景下，如果所有请求都直接打到 MySQL，很容易造成连接数耗尽、CPU 飙升甚至宕机。  

引入 Redis 缓存后，大部分读请求被 Redis 承接，只有缓存未命中时才访问 MySQL，大大降低了数据库的压力。  

二 Redis数据结构

Q4： Redis 数据类型以及使用场景分别是什么？  
String 类型的应⽤场景：缓存对象、常规计数、分布式锁、共享 session 信息等。  

List 类型的应⽤场景：消息队列（但是有两个问题：1. ⽣产者需要⾃⾏实现全局唯
⼀ ID；2. 不能以消费组形式消费数据）等。  

Hash 类型：缓存对象、购物车等。  

Set 类型：聚合计算（并集、交集、差集）场景，⽐如点赞、共同关注、抽奖活动
等。  

Zset 类型：排序场景，⽐如排⾏榜、电话和姓名排序等。  
BitMap（2.2 版新增）：⼆值状态统计的场景，⽐如签到、判断⽤户登陆状态、连
续签到⽤户总数等；  

HyperLogLog（2.8 版新增）：海量数据基数统计的场景，⽐如百万级⽹页 UV 计
数等；  

GEO（3.2 版新增）：存储地理位置信息的场景，⽐如滴滴叫车；  

Stream（5.0 版新增）：消息队列，相⽐于基于 List 类型实现的消息队列，有这两
个特有的特性：⾃动⽣成全局唯⼀消息ID，⽀持以消费组形式消费数据。  
  
Q5:五种常见的 Redis 数据类型是怎么实现？  
1. String 类型的底层的数据结构实现主要是 SDS（简单动态字符串）。SDS 和我们认识的 C 字符串不太⼀样，之所以没有使⽤ C 语⾔的字符串表⽰，因为 SDS 相
   ⽐于 C 的原⽣字符串：

SDS 不仅可以保存⽂本数据，还可以保存⼆进制数据。   （不依赖 \0 判断结尾，可以存储图片、音频等任意二进制数据）
SDS 获取字符串长度的时间复杂度是 O(1)。   （SDS 头部记录了 len 字段，不需要像 C 字符串那样遍历）
Redis 的 SDS API 是安全的，拼接字符串不会造成缓冲区溢出。  （修改前自动检查空间，不足时先扩容）
  
2. List  
   Redis 3.2 之前 List 底层是双向链表或压缩列表，3.2 之后统一为 quicklist。
   quicklist：宏观上是一个双向链表，每个节点（quicklistNode）指向一个 listpack（旧版是 ziplist）  
3. Hash
   Hash 类型的底层数据结构是由**压缩列表**或**哈希表**实现的：  

   如果哈希类型元素个数⼩于 512 个（默认值，可由 hash-max-ziplist-entries 配
   置），所有值⼩于 64 字节（默认值，可由 hash-max-ziplist-value 配置）的话，
   Redis 会使⽤压缩列表作为 Hash 类型的底层数据结构；
   如果哈希类型元素不满⾜上⾯条件，Redis 会使⽤哈希表作为 Hash 类型的底层数
   据结构。  

   在 Redis 7.0 中，压缩列表数据结构已经废弃了，交由 listpack 数据结构来实现了  
4. Set 类型内部实现  
   Set 类型的底层数据结构是由哈希表或整数集合实现的：
   如果集合中的元素都是整数且元素个数⼩于 512 （默认值，set-maxintset-entries
   配置）个，Redis 会使⽤整数集合作为 Set 类型的底层数据结构；
   如果集合中的元素不满⾜上⾯条件，则 Redis 使⽤哈希表作为 Set 类型的底层数据
   结构。  
5. ZSet 类型内部实现  
   Zset 类型的底层数据结构是由压缩列表或跳表实现的：
   如果有序集合的元素个数⼩于 128 个，并且每个元素的值⼩于 64 字节时，Redis
   会使⽤压缩列表作为 Zset 类型的底层数据结构；
   如果有序集合的元素不满⾜上⾯的条件，Redis 会使⽤跳表作为 Zset 类型的底层
   数据结构；  
  
三/ Redis线程模型  
Q6： Redis 是单线程吗  
Redis 单线程指的是「接收客户端请求->解析请求 ->进⾏数据读写等操作->发送数据给客
户端」这个过程是由⼀个线程（主线程）来完成的，这也是我们常说 Redis 是单线程的原
因。  
但是，Redis 程序并不是单线程的，Redis 在启动的时候，是会启动后台线程（BIO）的：关闭文件
AOF 刷盘（fsync）
释放内存（如异步删除大 key）   
  
Q7：Redis 采⽤单线程为什么还这么快？  
所有操作在内存中完成，速度极快。  

采用 I/O 多路复用机制（epoll/kqueue），单线程就能处理大量并发连接。  

数据结构简单，操作效率高。  

避免了多线程的上下文切换和锁竞争开销。  
  
Q8： 为什么早期 Redis 选择单线程？  
CPU 不是瓶颈：Redis 是内存数据库，性能瓶颈更多在内存大小和网络 I/O，而非 CPU。  

避免锁开销：单线程不需要加锁、解锁，没有线程切换和死锁问题，实现简单且可维护性高。  

多核利用：可以通过在一台机器上启动多个 Redis 实例（分片）来利用多核。  

Q9：Redis 6.0 之后为什么引⼊了多线程？  
这是因为随着⽹络硬件的性能提升，Redis 的性能瓶颈有时会出现在⽹络 I/O 的处理上  
但命令的执行仍然由主线程单线程处理，所以不存在多线程同时执行命令的问题。  
线程数建议设置为 CPU 核数的一半左右（如 4 核设 2~3，8 核设 6），且不能超过核数。  

四/Redis持久化  
Q10：Redis 如何实现数据不丢失？  
Redis 共有三种数据持久化的⽅式：  

AOF ⽇志：每执⾏⼀条写操作命令，就把该命令以追加的⽅式写⼊到⼀个⽂件
⾥；  

RDB 快照：将某⼀时刻的内存数据，以⼆进制的⽅式写⼊磁盘；  

混合持久化⽅式：Redis  4.0 新增的⽅式，集成了 AOF 和 RDB 的优点；  
  
Q11: AOF 日志是如何实现的？  
Redis 在执⾏完⼀条写操作命令后，就会把该命令以追加的⽅式写⼊到⼀个⽂件⾥，然后
Redis 重启时，会读取该⽂件记录的命令，然后逐⼀执⾏命令的⽅式来进⾏数据恢复  
  
Q12:为什么先执行命令，再把数据写入日志呢？  
Reids 是先执⾏写操作命令后，才将该命令记录到 AOF ⽇志⾥的，这么做其实有两个好
处。  

避免额外的检查开销：因为如果先将写操作命令记录到 AOF ⽇志⾥，再执⾏该命
令的话，如果当前的命令语法有问题，那么如果不进⾏命令语法检查，该错误的命
令记录到 AOF ⽇志⾥后，Redis 在使⽤⽇志恢复数据时，就可能会出错。  

不会阻塞当前写操作命令的执⾏：因为当写操作命令执⾏成功后，才会将命令记录
到 AOF ⽇志。  

当然，这样做也会带来风险：  

数据可能会丢失： 执⾏写操作命令和记录⽇志是两个过程，那当 Redis 在还没来
得及将命令写⼊到硬盘时，服务器发⽣宕机了，这个数据就会有丢失的风险。  

可能阻塞其他操作： 由于写操作命令执⾏成功后才记录到 AOF ⽇志，所以不会阻
塞当前命令的执⾏，但因为 AOF ⽇志也是在主线程中执⾏，所以当 Redis 把⽇志
⽂件写⼊磁盘的时候，还是会阻塞后续的操作⽆法执⾏。

Q14:AOF 日志过大，会触发什么机制？  
AOF 重写机制，
