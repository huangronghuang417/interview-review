
REDIS
一 认识redis
Q1 ：什么是redis    

Redis 是⼀种基于内存的数据库，对数据的读写操作都是在内存中完成，因此读写速度⾮常
快，常⽤于缓存，消息队列、分布式锁等场景。  
  

Redis 提供了多种数据类型来⽀持不同的业务场景，⽐如 String(字符串)、Hash(哈希)、
List (列表)、Set(集合)、Zset(有序集合)、Bitmaps（位图）、HyperLogLog（基数统计）、
GEO（地理信息）、Stream（流），并且对数据类型的操作都是原⼦性的，因为执⾏命令
由单线程负责的，不存在并发竞争的问题。  

除此之外，Redis 还⽀持事务 、持久化、Lua 脚本、多种集群⽅案（主从复制模式、哨兵模
式、切⽚机群模式）、发布/订阅模式，内存淘汰机制、过期删除机制等等。
  
Q2   Redis 和 Memcached 有什么区别？
Redis 与 Memcached 共同点：
1. 都是基于内存的数据库，⼀般都⽤来当做缓存使⽤。
2. 都有过期策略。
3. 两者的性能都⾮常⾼。  

**Redis 与 Memcached 区别：**  
  

   Redis ⽀持的数据类型更丰富（String、Hash、List、Set、ZSet），⽽
   Memcached 只⽀持最简单的 key-value 数据类型；  

   Redis ⽀持数据的持久化，可以将内存中的数据保持在磁盘中，重启的时候可以再
   次加载进⾏使⽤，⽽ Memcached 没有持久化功能，数据全部存在内存之中，
   Memcached 重启或者挂掉后，数据就没了；  

   Redis 原⽣⽀持集群模式，Memcached 没有原⽣的集群模式，需要依靠客户端来
   实现往集群中分⽚写⼊数据；  

   Redis ⽀持发布订阅模型、Lua 脚本、事务等功能，⽽ Memcached 不⽀持；   
     
Q3：为什么用 Redis 作为 MySQL 的缓存？  
主要是因为 Redis 具备「⾼性能」和「⾼并发」两种特性。  
1. 高性能（读写速度快）

MySQL 是磁盘数据库，数据存储在硬盘上，读写涉及磁盘 I/O，延迟较高（毫秒级）。  

Redis 是内存数据库，所有数据读写都在内存中完成，速度极快（纳秒~微秒级）。  

将热点数据缓存到 Redis 中，后续请求直接从内存读取，避免频繁访问 MySQL，响应时间从毫秒级降到微秒级。  

2. 高并发（支撑更高 QPS）

Redis 单机的 QPS（每秒查询率）轻松突破 10 万，而 MySQL 单机很难破 1 万。  

在高并发场景下，如果所有请求都直接打到 MySQL，很容易造成连接数耗尽、CPU 飙升甚至宕机。  

引入 Redis 缓存后，大部分读请求被 Redis 承接，只有缓存未命中时才访问 MySQL，大大降低了数据库的压力。  

二 Redis数据结构

Q4： Redis 数据类型以及使用场景分别是什么？  
String 类型的应⽤场景：缓存对象、常规计数、分布式锁、共享 session 信息等。  

List 类型的应⽤场景：消息队列（但是有两个问题：1. ⽣产者需要⾃⾏实现全局唯
⼀ ID；2. 不能以消费组形式消费数据）等。  

Hash 类型：缓存对象、购物车等。  

Set 类型：聚合计算（并集、交集、差集）场景，⽐如点赞、共同关注、抽奖活动
等。  

Zset 类型：排序场景，⽐如排⾏榜、电话和姓名排序等。  
BitMap（2.2 版新增）：⼆值状态统计的场景，⽐如签到、判断⽤户登陆状态、连
续签到⽤户总数等；  

HyperLogLog（2.8 版新增）：海量数据基数统计的场景，⽐如百万级⽹页 UV 计
数等；  

GEO（3.2 版新增）：存储地理位置信息的场景，⽐如滴滴叫车；  

Stream（5.0 版新增）：消息队列，相⽐于基于 List 类型实现的消息队列，有这两
个特有的特性：⾃动⽣成全局唯⼀消息ID，⽀持以消费组形式消费数据。  
  
Q5:五种常见的 Redis 数据类型是怎么实现？  
1. String 类型的底层的数据结构实现主要是 SDS（简单动态字符串）。SDS 和我们认识的 C 字符串不太⼀样，之所以没有使⽤ C 语⾔的字符串表⽰，因为 SDS 相
   ⽐于 C 的原⽣字符串：

SDS 不仅可以保存⽂本数据，还可以保存⼆进制数据。   （不依赖 \0 判断结尾，可以存储图片、音频等任意二进制数据）
  
SDS 获取字符串长度的时间复杂度是 O(1)。   （SDS 头部记录了 len 字段，不需要像 C 字符串那样遍历）
  
Redis 的 SDS API 是安全的，拼接字符串不会造成缓冲区溢出。  （修改前自动检查空间，不足时先扩容）
  
2. List  
   Redis 3.2 之前 List 底层是双向链表或压缩列表，3.2 之后统一为 quicklist。
   quicklist：宏观上是一个双向链表，每个节点（quicklistNode）指向一个 listpack（旧版是 ziplist）  
3. Hash
   Hash 类型的底层数据结构是由**压缩列表**或**哈希表**实现的：  

   如果哈希类型元素个数⼩于 512 个（默认值，可由 hash-max-ziplist-entries 配
   置），所有值⼩于 64 字节（默认值，可由 hash-max-ziplist-value 配置）的话，
   Redis 会使⽤压缩列表作为 Hash 类型的底层数据结构；
   如果哈希类型元素不满⾜上⾯条件，Redis 会使⽤哈希表作为 Hash 类型的底层数
   据结构。  

   在 Redis 7.0 中，压缩列表数据结构已经废弃了，交由 listpack 数据结构来实现了  
4. Set 类型内部实现  
   Set 类型的底层数据结构是由哈希表或整数集合实现的：
   如果集合中的元素都是整数且元素个数⼩于 512 （默认值，set-maxintset-entries
   配置）个，Redis 会使⽤整数集合作为 Set 类型的底层数据结构；
   如果集合中的元素不满⾜上⾯条件，则 Redis 使⽤哈希表作为 Set 类型的底层数据
   结构。  
5. ZSet 类型内部实现  
   Zset 类型的底层数据结构是由压缩列表或跳表实现的：
   如果有序集合的元素个数⼩于 128 个，并且每个元素的值⼩于 64 字节时，Redis
   会使⽤压缩列表作为 Zset 类型的底层数据结构；
   如果有序集合的元素不满⾜上⾯的条件，Redis 会使⽤跳表作为 Zset 类型的底层
   数据结构；  
  
三/ Redis线程模型  
Q6： Redis 是单线程吗  
Redis 单线程指的是「接收客户端请求->解析请求 ->进⾏数据读写等操作->发送数据给客
户端」这个过程是由⼀个线程（主线程）来完成的，这也是我们常说 Redis 是单线程的原
因。  
但是，Redis 程序并不是单线程的，Redis 在启动的时候，是会启动后台线程（BIO）的：关闭文件
AOF 刷盘（fsync）
释放内存（如异步删除大 key）   
  
Q7：Redis 采⽤单线程为什么还这么快？  
所有操作在内存中完成，速度极快。  

采用 I/O 多路复用机制（epoll/kqueue），单线程就能处理大量并发连接。  

数据结构简单，操作效率高。  

避免了多线程的上下文切换和锁竞争开销。  
  
Q8： 为什么早期 Redis 选择单线程？  
CPU 不是瓶颈：Redis 是内存数据库，性能瓶颈更多在内存大小和网络 I/O，而非 CPU。  

避免锁开销：单线程不需要加锁、解锁，没有线程切换和死锁问题，实现简单且可维护性高。  

多核利用：可以通过在一台机器上启动多个 Redis 实例（分片）来利用多核。  

Q9：Redis 6.0 之后为什么引⼊了多线程？  
这是因为随着⽹络硬件的性能提升，Redis 的性能瓶颈有时会出现在⽹络 I/O 的处理上  
所以为了提高网络 I/O 的并行度，Redis 6.0 对于网络 I/O 采用多线程来处理。但命令的执行仍然由主线程单线程处理，所以不存在多线程同时执行命令的问题。  
线程数建议设置为 CPU 核数的一半左右（如 4 核设 2~3，8 核设 6），且不能超过核数。  

四/Redis持久化  
Q10：Redis 如何实现数据不丢失？  
Redis 共有三种数据持久化的⽅式：  

AOF ⽇志：每执⾏⼀条写操作命令，就把该命令以追加的⽅式写⼊到⼀个⽂件
⾥；  

RDB 快照：将某⼀时刻的内存数据，以⼆进制的⽅式写⼊磁盘；  

混合持久化⽅式：Redis  4.0 新增的⽅式，集成了 AOF 和 RDB 的优点；  
  
Q11: AOF 日志是如何实现的？  
Redis 在执⾏完⼀条写操作命令后，就会把该命令以追加的⽅式写⼊到⼀个⽂件⾥，然后
Redis 重启时，会读取该⽂件记录的命令，然后逐⼀执⾏命令的⽅式来进⾏数据恢复  
  
Q12:为什么先执行命令，再把数据写入日志呢？  
Reids 是先执⾏写操作命令后，才将该命令记录到 AOF ⽇志⾥的，这么做其实有两个好
处。  

避免额外的检查开销：因为如果先将写操作命令记录到 AOF ⽇志⾥，再执⾏该命
令的话，如果当前的命令语法有问题，那么如果不进⾏命令语法检查，该错误的命
令记录到 AOF ⽇志⾥后，Redis 在使⽤⽇志恢复数据时，就可能会出错。  

不会阻塞当前写操作命令的执⾏：因为当写操作命令执⾏成功后，才会将命令记录
到 AOF ⽇志。  

当然，这样做也会带来风险：  

数据可能会丢失： 执⾏写操作命令和记录⽇志是两个过程，那当 Redis 在还没来
得及将命令写⼊到硬盘时，服务器发⽣宕机了，这个数据就会有丢失的风险。  

可能阻塞其他操作： 由于写操作命令执⾏成功后才记录到 AOF ⽇志，所以不会阻
塞当前命令的执⾏，但因为 AOF ⽇志也是在主线程中执⾏，所以当 Redis 把⽇志
⽂件写⼊磁盘的时候，还是会阻塞后续的操作⽆法执⾏。

Q14:AOF 日志过大，会触发什么机制？  
Redis 为了避免 AOF ⽂件越写越⼤，提供了 AOF 重写机制
AOF 重写机制是在重写时，读取当前数据库中的所有键值对，然后将每⼀个键值对⽤⼀条
命令记录到「新的 AOF ⽂件」，等到全部记录完后，就将新的 AOF ⽂件替换掉现有的 AOF
⽂件

Q15  重写 AOF 日志的过程是怎样的？
1. Redis 的重写 AOF 过程是由后台⼦进程 bgrewriteaof 来完成的，
2. 主进程 fork 子进程  
   Redis 会 fork 一个子进程（bgrewriteaof）来做重写，不阻塞主线程处理客户端请求。  
   fork 时通过写时复制（COW）共享内存：子进程复制主进程的页表，不复制物理内存，只有主进程后续修改某块内存页时才真正拷贝那份数据  
3. 子进程扫描内存，生成新 AOF  
   子进程遍历所有数据库的键值对，把每个 key 当前的值转成一条（或几条）写命令，写入临时新 AOF 文件。  
4. 重写期间主进程继续处理写命令  
   主进程不中断服务，新写命令会同时写两处：

原 AOF 缓冲区​ → 继续追加到旧 AOF 文件（保证旧文件完整，重写失败也不丢数据）
  
AOF 重写缓冲区​ → 记录 fork 之后产生的新命令  
因为子进程拿到的是 fork 那一刻的内存快照，fork 之后的修改它感知不到，所以需要这个重写缓冲区来补  
5. 子进程完成，主进程收尾替换  
   子进程写完后发信号通知主进程。  

   主进程把 AOF 重写缓冲区里的增量命令追加到临时新 AOF 文件末尾，保证新文件和当前内存状态一致。
     
   然后用 rename 原子替换旧 AOF 文件。
     
    后续新命令直接写新 AOF 文件，重写结束。  
  
Q16 追问：为什么用子进程，不用线程  
用线程会和主线程共享内存，主线程改数据时要加锁，性能下降。  

用子进程 + 写时复制：fork 只复制页表，物理内存父子共享且只读；主进程写某页时才拷贝那一页（COW），不需要全局加锁。
  
Q17：RDB 做快照时会阻塞线程吗？  
Redis 提供了两个命令来生成 RDB 文件，分别是 save 和 bgsave，RDB 快照是否阻塞线程，取决于使用哪种方式触发：  
1. SAVE 命令 —— 会阻塞

SAVE 是在主线程中直接生成 RDB 文件的，执行期间 Redis 主线程被完全占用  
2. BGSAVE 命令 —— 不会阻塞主线程（推荐方式）

BGSAVE 会调用 fork() 创建一个子进程来生成 RDB 文件，主线程继续处理客户端请求，不阻塞。
不过要注意：fork 操作本身会短暂阻塞主线程（需要复制页表），数据量越大页表越大，阻塞时间越长，但 fork 完成后主线程就立即恢复工作了。  
3. 自动触发 —— 也是 BGSAVE

Redis 配置文件里的 save m n 规则（如 save 900 1），到达条件后自动执行的也是 BGSAVE，不会阻塞主线程。  

Q18： RDB 在执行快照的时候，数据能修改吗？  
可以，执⾏ bgsave 过程中，Redis 依然可以继续处理操作命令，子进程和主进程通过写时复制（COW）共享内存：子进程只读内存生成快照，主进程修改数据时触发 COW 拷贝，互不影响。  
  
Q19：为什么会有混合持久化  
答：AOF的优点是丢失数据少，但数据恢复不快；RDB优点是数据恢复快，但快照频率不好把握：频率太低，丢失的数据就比较多，频率太高，就会影响性能  
为集成两者的优点，Redis4.0提出了混合使用AOF日志和内存快照，也叫混合持久化，既保证了重启速度，又降低了数据丢失风险  
混合持久化工作在AOF日志重写过程，AOF重写日志时，fork出来的重写子进程会先将与主进程共享的内存数据以RDB方式写入AOF文件，然后主线程处理的操作命令会被记录在重写缓冲区里，重写缓冲区里的增量命令会以AOF方式写入AOF文件，写入完成后通知主进程将新的含有RDB格式和AOF格式的AOF文件替换旧的AOF文件  
也就是说，使⽤了混合持久化，AOF ⽂件的前半部分是 RDB 格式的全量数据，后半部分是
AOF 格式的增量数据。    
  
Q20:混合持久化优缺点：  

混合持久化优点：  

混合持久化结合了 RDB 和 AOF 持久化的优点，开头为 RDB 的格式，使得 Redis
可以更快的启动，同时结合 AOF 的优点，有减低了⼤量数据丢失的风险。  

混合持久化缺点：  

AOF ⽂件中添加了 RDB 格式的内容，使得 AOF ⽂件的可读性变得很差；
兼容性差，如果开启混合持久化，那么此混合持久化 AOF ⽂件，就不能⽤在
Redis 4.0 之前版本了。  
  
**REDIS集群**  
  
Q21:Redis 如何实现服务⾼可⽤？  
Redis 高可用是多层机制叠加的：

1. 主从复制 — 基础

一主多从，读写分离。主节点异步将写命令同步给从节点，不等待从节点执行结果返回客户端，所以主从数据无法强一致，短时间不一致是必然的。主从复制分为全量同步（首次连接）和增量同步（断线重连后通过 repl_backlog 补发），这是数据冗余和读写分离的基础，但主从本身不会自动切换。

2. 哨兵模式 — 自动故障转移

哨兵是独立进程，负责监控、通知、自动故障转移。单个哨兵 PING 超时标记主观下线，达到 quorum 个哨兵同意才标记客观下线（防误判）。之后哨兵间选领导者，由领导者选优先级高、复制偏移量大的从节点提升为新主，其余从节点跟随，客户端收到通知重连新主。部署至少 3 个哨兵分散在不同机器。

3. Redis Cluster — 分片 + 高可用

数据量大时用 Cluster，同时解决水平扩容和分片级故障转移。16384 个哈希槽按 CRC16(key) % 16384 映射到不同主节点，每个主节点挂从节点。主节点宕机时从节点自动提升为新主，槽位不变，客户端通过 MOVED 重定向。节点间 Gossip 协议互通，自带故障检测，不需要额外部署哨兵。

总结：主从做冗余和读写分离，哨兵做自动切换（小规模），Cluster 做分片+切换（大规模），三者配合持久化（RDB/AOF）做兜底，共同实现高可用。  

Q22：集群脑裂导致数据丢失怎么办？
脑裂问题：在 Redis 主从架构中，如果主节点与从节点之间网络断开（但主节点和客户端网络正常），哨兵会认为主节点挂了，从从节点中选举出新主节点。此时集群出现两个主节点（旧主+新主），客户端还在往旧主写数据。网络恢复后，旧主被降级为从节点，清空本地数据重新全量同步，导致网络分区期间写入旧主的数据全部丢失。

解决方案：Redis 提供了两个参数来预防脑裂丢数据：

min-slaves-to-write：主节点至少要有 N 个从节点连接，否则拒绝写请求
min-slaves-max-lag：从节点与主节点的 ACK 延迟不能超过 T 秒，否则认为从节点不健康，不计入有效从节点数

两者搭配使用：当主节点连接的健康从节点数 < 设定值时，主节点直接返回错误，不再接受任何写请求。


**Redis 过期删除与内存淘汰**  
  
Q23： Redis 使⽤的过期删除策略是什么？    
Redis 使用的过期删除策略是「惰性删除 + 定期删除」两种策略配合使用。

1. 惰性删除

做法：不主动删除过期键，每次从数据库访问 key 时，都检测 key 是否过期，如果过期则删除该 key。
优点：对 CPU 友好，只在访问时才检查，不浪费 CPU 时间。
缺点：对内存不友好，如果过期键一直不被访问，就会一直占用内存，造成内存泄漏。

2. 定期删除

做法：每隔一段时间，随机从数据库中取出一定数量的 key 进行检查，并删除其中的过期 key。
流程细节（面试加分项）：
Redis 默认每秒进行 10 次过期扫描（可配置 hz 参数）。
每次扫描随机取 20 个 key，删除其中过期的。
如果过期 key 比例超过 25%，就继续重复这个过程，直到比例低于 25% 或单次循环超时（默认不超过 25ms）就退出。
优点：通过限制时长和频率，减少了对 CPU 的占用；定期清理部分过期键，减少了内存浪费。
缺点：难以精确确定删除操作的时长和频率，如果执行太频繁会占用 CPU，太少则内存浪费。

为什么配合使用？

惰性删除对 CPU 最友好，但可能漏掉不常访问的过期键，导致内存浪费。
定期删除可以主动清理一部分过期键，弥补惰性删除的不足，同时通过限制执行时间和频率，避免阻塞主线程。
两者结合，在合理使用 CPU 时间和避免内存浪费之间取得平衡。  

## Q24: Redis 持久化时，对过期键会如何处理的？  
Redis 持久化分为 RDB 和 AOF 两种方式，对过期键的处理逻辑不同，但核心原则都是不把已过期的键持久化为有效数据。

### 一、RDB 持久化
  
#### 生成 RDB 文件（执行 SAVE 或 BGSAVE）：
Redis 会检查每个 key 的过期时间，如果 key 已经过期，则不会写入​ RDB 文件。
  
#### 加载 RDB 文件（Redis 启动恢复数据）：
如果以主服务器模式运行：会检查 RDB 中的 key，已过期的 key 会被直接忽略，不会加载到数据库。
如果以从服务器模式运行：会载入 RDB 中所有​ key（包括过期 key），因为从库在同步主库时，会先清空本地数据再全量同步，之后主库会通过复制流发送 DEL 命令来删除过期键（从库自身不主动进行过期扫描）。

### 二、AOF 持久化

#### AOF 写入（命令传播阶段）：
当过期键被删除（通过惰性删除或定期删除）时，Redis 会向 AOF 文件追加一条 DEL 命令，记录该 key 已被删除。这样 AOF 文件中虽然保留了之前的写命令，但最后有 DEL 标记，恢复时不会重新写入过期数据。

#### AOF 重写：
重写时会扫描当前数据库，已过期的 key 不会写入新的 AOF 文件，因此重写后的 AOF 文件只包含未过期的键值对。

  
## Q25:Redis 主从模式中，对过期键会如何处理？

当 Redis 运⾏在主从模式下时，从库不会进⾏过期扫描，从库对过期的处理是被动的。也就
是即使从库中的 key 过期了，如果有客户端访问从库时，依然可以得到 key 对应的值，像
未过期的键值对⼀样返回。  

从库的过期键处理依靠主服务器控制，主库在 key 到期时，会在 AOF ⽂件⾥增加⼀条 del
指令，同步到所有的从库，从库通过执⾏这条 del 指令来删除过期的 key。  
  
## Q26:  Redis 内存满了，会发⽣什么？  
在 Redis 的运⾏内存达到了某个阀值，就会触发内存淘汰机制，这个阀值就是我们设置的最
⼤运⾏内存，此值在 Redis 的配置⽂件中可以找到，配置项为 maxmemory。  
  
## Q27:Redis 内存淘汰策略有哪些？  
Redis 内存淘汰策略共有⼋种，这⼋种策略⼤体分为「不进⾏数据淘汰」和「进⾏数据淘
汰」两类策略。  
### 1、不进⾏数据淘汰的策略
noeviction（Redis3.0之后，默认的内存淘汰策略） ：它表⽰当运⾏内存超过最⼤设置内
存时，不淘汰任何数据，⽽是不再提供服务，直接返回错误。
### 2、进⾏数据淘汰的策略
针对「进⾏数据淘汰」这⼀类策略，又可以细分为「在设置了过期时间的数据中进⾏淘汰」
和「在所有数据范围内进⾏淘汰」这两类策略。
在设置了过期时间的数据中进⾏淘汰：  

`volatile-random：`随机淘汰设置了过期时间的任意键值；  
`volatile-ttl：`优先淘汰更早过期的键值。  
`volatile-lru`（Redis3.0 之前，默认的内存淘汰策略）：淘汰所有设置了过期时间
的键值中，最久未使⽤的键值；  
`volatile-lfu`（Redis 4.0 后新增的内存淘汰策略）：淘汰所有设置了过期时间的键
值中，最少使⽤的键值；  

在所有数据范围内进⾏淘汰：  

`allkeys-random：`随机淘汰任意键值;  
`allkeys-lru：`淘汰整个键值中最久未使⽤的键值；  
`allkeys-lfu`（Redis 4.0 后新增的内存淘汰策略）：淘汰整个键值中最少使⽤的键
值。  
  
## Q28 LRU 算法和 LFU 算法有什么区别？
### 什么是 LRU 算法？
LRU 全称是 Least Recently Used 翻译为最近最少使⽤，会选择淘汰最近最少使⽤的数据。  
### Q29 Redis 是如何实现 LRU 算法的？
Redis 实现的是⼀种近似 LRU 算法，⽬的是为了更好的节约内存，它的实现⽅式是在
Redis 的对象结构体中添加⼀个额外的字段，⽤于记录此数据的最后⼀次访问时间。
  
当 Redis 进⾏内存淘汰时，会使⽤随机采样的⽅式来淘汰数据，它是随机取 5 个值（此值可
配置），然后淘汰最久没有使⽤的那个。
  
Redis 实现的 LRU 算法的优点：
  
不⽤为所有的数据维护⼀个⼤链表，节省了空间占⽤；
不⽤在每次数据访问时都移动链表项，提升了缓存的性能；
  
但是 LRU 算法有⼀个问题，⽆法解决缓存污染问题，⽐如应⽤⼀次读取了⼤量的数据，⽽
这些数据只会被读取这⼀次，那么这些数据会留存在 Redis 缓存中很长⼀段时间，造成缓存
污染。  
  
### Q30 什么是 LFU 算法
LFU 全称是 Least Frequently Used 翻译为最近最不常⽤的，LFU 算法是根据数据访问次数
来淘汰数据的，它的核⼼思想是“如果数据过去被访问多次，那么将来被访问的频率也更
⾼”。
  
所以， LFU 算法会记录每个数据的访问次数。当⼀个数据被再次访问时，就会增加该数据
的访问次数。这样就解决了偶尔被访问⼀次之后，数据留存在缓存中很长⼀段时间的问题，
相⽐于 LRU 算法也更合理⼀些。
  
### Q31 Redis 是如何实现 LFU 算法的？  
LFU 算法相⽐于 LRU 算法的实现，多记录了「数据的访问频次」的信息。Redis 对象的结
构如下  
![](https://raw.githubusercontent.com/huangronghuang417/interview-review/main/images/puTecS.png)
Redis 对象头中的 lru 字段，在 LRU 算法下和 LFU 算法下使⽤⽅式并不相同。
  
在 LRU 算法中，Redis 对象头的 24 bits 的 lru 字段是⽤来记录 key 的访问时间戳，因此在
LRU 模式下，Redis可以根据对象头中的 lru 字段记录的值，来⽐较最后⼀次 key 的访问时
间长，从⽽淘汰最久未被使⽤的 key。
  
在 LFU 算法中，Redis对象头的 24 bits 的 lru 字段被分成两段来存储，⾼ 16bit 存储
ldt(Last Decrement Time)，⽤来记录 key 的访问时间戳；低 8bit 存储 logc(Logistic
Counter)，⽤来记录 key 的访问频次。  
  
## Redis缓存设计  
### Q32 如何避免缓存雪崩
当⼤量缓存数据在同⼀时间过期（失效）时，如果此时有⼤量的⽤户请求，都⽆法在
Redis 中处理，于是全部请求都直接访问数据库，从⽽导致数据库的压⼒骤增，严重的会造
成数据库宕机，从⽽形成⼀系列连锁反应，造成整个系统崩溃，这就是缓存雪崩的问题。  
有两种解决方案：  
1. **将缓存失效时间随机打散**： 我们可以在原有的失效时间基础上增加⼀个随机值
   （⽐如 1 到 10 分钟）这样每个缓存的过期时间都不重复了，也就降低了缓存集体
   失效的概率。  
2. **设置缓存不过期**： 我们可以通过后台服务来更新缓存数据，从⽽避免因为缓存失
   效造成的缓存雪崩，也可以在⼀定程度上避免缓存并发问题。  
  
### Q33 如何避免缓存击穿？
如果缓存中的某个热点数据过期了，此时⼤量的请求访问了该热点数据，就⽆法从缓存中读
取，直接访问数据库，数据库很容易就被**⾼并发**的请求冲垮，这就是缓存击穿的问题。（可以认为缓存击穿是缓存雪崩的⼀个⼦集。）  
两种⽅案：  
1. 互斥锁⽅案（Redis 中使⽤ setNX ⽅法设置⼀个状态位，表⽰这是⼀种锁定状
   态），保证同⼀时间只有⼀个业务线程请求缓存，未能获取互斥锁的请求，要么等
   待锁释放后重新读取缓存，要么就返回空值或者默认值。  
2. 不给热点数据设置过期时间，由后台异步更新缓存，或者在热点数据准备要过期
   前，提前通知后台线程更新缓存以及重新设置过期时间；  
  
### Q34  如何避免缓存穿透？
缓存穿透是指用户请求的数据既不在缓存中，也不在数据库里，导致每次请求都要穿透到数据库查询，如果大量此类请求涌来，数据库压力骤增甚至宕机。

常见解决方案有三种：

1. 缓存空值（缓存无效 key）

当数据库查询不到数据时，仍然把这个“空结果”缓存起来（比如 SET key null 30），并设置一个较短的过期时间（如 30~60 秒）。
后续相同请求先查缓存，命中空值直接返回，不再访问数据库。
优点：实现简单，能快速拦截重复请求。
缺点：如果恶意攻击使用大量不同的不存在 key，缓存层会存大量空值，可能耗尽内存；需要对所有不存在的 key 都缓存，内存浪费。

2. 布隆过滤器（Bloom Filter）

在缓存层之前加一个布隆过滤器，将所有可能存在的数据 key​ 哈希到一个足够大的 bitmap 中。
请求进来时，先通过布隆过滤器判断 key 是否存在：
如果过滤器说不存在，则直接返回，连缓存都不用查。
如果过滤器说存在，则继续查缓存 → 查数据库。
优点：内存占用极小，能拦截几乎所有不存在的 key，适合海量数据场景。
缺点：布隆过滤器有误判率（说存在但实际不存在），且不支持删除操作（可用 Counting Bloom Filter 改进）；初始构建过滤器需要全量数据。

3. 接口层增加校验（请求合法性过滤）

在 API 入口做参数校验、用户鉴权、限流等，比如：id 格式校验（是否为合法 UUID/数字）、用户登录态校验、对同一 IP/用户频繁请求不存在 key 的行为进行限流或熔断。
优点：从源头减少非法请求。
缺点：无法完全防止精心构造的合法格式但不存在 key 的攻击，需配合其他方案。

实际生产中通常组合使用：接口校验 + 布隆过滤器 + 缓存空值，形成多层防护。  
  
## Q35 如何设计一个缓存策略，可以动态缓存热点数据呢？
由于数据存储受限，系统并不是将所有数据都需要存放到缓存中的，⽽只是将**其中⼀部分热

热点数据动态缓存的策略总体思路：通过数据最新访问时间来做排名，并过滤掉不常访问的
数据，只留下经常访问的数据。

## Q36 说说常见的缓存更新策略？  
常见的缓存更新策略共有3种：  

Cache Aside（旁路缓存）策略；  

Read/Write Through（读穿 / 写穿）策略；  

Write Back（写回）策略；  

实际开发中，Redis 和 MySQL 的更新策略⽤的是 Cache Aside，另外两种策略应⽤不了。  
  
### Cache Aside（旁路缓存）策略
常见的缓存更新策略共有三种：Cache Aside（旁路缓存）、Read/Write Through（读穿/写穿）、Write Back（写回）。实际开发中，最常用的是 Cache Aside，另外两种应用较少。

1. Cache Aside（旁路缓存）策略

这是最常用的策略，应用程序直接与数据库、缓存交互，并负责缓存的维护。分为读策略和写策略：

读策略：先读缓存，如果命中直接返回；如果未命中，则从数据库读取，然后写入缓存，再返回。
写策略：先更新数据库，再删除缓存（不是更新缓存）。
为什么是删除缓存而不是更新缓存？​ 如果更新缓存，在并发写+读场景下可能导致数据不一致；而删除缓存后，下次读请求会加载最新数据，保证一致性。
为什么先更新数据库再删除缓存？​ 如果顺序颠倒（先删缓存再更新数据库），在并发读+写下可能出现缓存和数据库数据不一致。先更新数据库再删除缓存，虽然理论上也有极小概率不一致，但因为缓存写入通常比数据库写入快，实际中几乎不会出现。
适用场景：读多写少的场景。如果写入频繁，缓存会被频繁删除，命中率下降，可考虑其他方案。

2. Read/Write Through（读穿/写穿）策略

原则是应用程序只和缓存交互，不再和数据库直接交互，由缓存组件负责和数据库交互。

Read Through：读数据时，如果缓存未命中，由缓存组件从数据库加载数据并写入缓存，再返回给应用。
Write Through：写数据时，如果数据在缓存中存在，则更新缓存，并由缓存组件同步更新数据库；如果缓存中不存在，则直接更新数据库（或称为Write Around）。
特点：对应用透明，但常用的分布式缓存（如Redis）一般不提供自动同步数据库的功能，所以较少使用。

3. Write Back（写回）策略

更新数据时，只更新缓存，并将缓存标记为脏数据，然后立即返回，并不更新数据库。数据库更新通过异步批量方式进行。

优点：写性能极高，适合写多的场景。
缺点：数据不是强一致性的，且存在数据丢失风险（缓存宕机导致脏数据未落盘）。
应用：计算机体系结构中的CPU缓存、操作系统文件系统的Page Cache等，但Redis本身没有异步更新数据库的功能，所以一般不直接用于数据库+缓存场景。

总结：实际项目中，我们基本都用 Cache Aside 策略，配合过期时间、消息队列重试删除等机制来保证数据一致性。
