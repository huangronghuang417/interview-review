锁：  
面试题  
第一梯队：必考  
1， InnoDB 有哪些类型的锁？  
答： InnoDB 锁按粒度分：表锁和行锁。行锁按算法分三种：Record Lock（记录锁，锁单条索引记录）、Gap Lock（间隙锁，锁两个索引之间的间隙）、Next-Key Lock（Record + Gap，左开右闭区间，InnoDB 默认）。按模式分：S锁（共享锁，读锁）和X锁（排他锁，写锁）。还有表级的意向锁（IS/IX），是 InnoDB 自动加的，用于快速判断表里有没有行被锁。  
2， 什么是 Next-Key Lock？为什么 InnoDB 默认用它？  
答： Next-Key Lock 是 Record Lock + Gap Lock 的组合，锁定范围是左开右闭区间 (前一条记录, 当前记录]。InnoDB 在 RR 隔离级别下默认使用它，主要解决当前读场景的幻读问题——通过 Gap Lock 锁住间隙，防止其他事务插入新行。唯一索引等值查询命中时会退化为纯 Record Lock，未命中时退化为 Gap Lock。  
3   不同查询条件下，InnoDB 分别加什么锁？  
答： 唯一索引等值查询命中​ → 退化为 Record Lock；未命中​ → 退化为 Gap Lock。

唯一索引范围查询​ → Next-Key Lock，不退化。

非唯一索引等值查询​ → Next-Key Lock + 下一个记录加 Gap Lock。

非唯一索引范围查询​ → Next-Key Lock，不退化。

没走索引的 UPDATE/DELETE​ → 全表聚簇索引每行加 Record Lock，等于锁全表。  

4   死锁产生的四个必要条件是什么？  
答： 互斥，占有且等待，不可强占用，循环等待  
（解释）：① 互斥：资源不能被共享，只能由一个事务持有；

② 占有且等待：事务持有至少一个锁，又在等待获取其他锁；

③ 不可强占用：已分配给事务的锁不能被强制剥夺，只能事务自己释放；

④ 循环等待：多个事务形成头尾相接的循环等待关系。  
  
5 InnoDB 怎么检测和处理死锁？  
答 ： 检测：通过等待图（Wait-For Graph），每次事务请求锁被阻塞时检查是否形成环。  

处理：选择回滚代价最小的事务（按 undo log 量判断）作为牺牲品回滚，抛出 Deadlock found 错误，另一个事务继续执行。应用层需要捕获异常后重试。  
  
6     遇到死锁怎么排查和解决？  
答：  
排查：SHOW ENGINE INNODB STATUS 查看最近一次死锁详情（涉及的事务、SQL、持有的锁、等待的锁）。

解决：最根本的是统一加锁顺序（所有事务按相同顺序获取锁）；其他手段包括缩小事务范围减少锁持有时间、降低隔离级别到 RC 减少 Gap Lock、合理设计索引避免锁全表、应用层加重试机制。  
  
第二梯队：  
Q7：两阶段锁协议是什么？对事务设计有什么影响？

InnoDB 遵循两阶段锁协议：加锁阶段在执行 SQL 时逐个加锁，解锁阶段在事务 COMMIT 或 ROLLBACK 时一次性释放所有锁。影响：事务越晚提交，锁持有时间越长，越容易阻塞其他事务。所以尽量把事务写短、尽快提交，把非数据库操作（RPC、IO）移出事务。  

Q8：为什么说"行锁加在索引上"？没走索引会怎样？

InnoDB 的行锁是加在索引记录上的，不是加在数据行本身。如果 WHERE 条件没走索引（全表扫描），会对每一行聚簇索引记录加 Record Lock，效果等同于锁全表。所以 UPDATE/DELETE 的 WHERE 条件一定要走索引。  

Q9：SELECT ... FOR UPDATE 和 SELECT ... LOCK IN SHARE MODE 的区别？

FOR UPDATE 加 X锁（排他锁），其他事务不能加任何锁也不能修改；LOCK IN SHARE MODE 加 S锁（共享锁），其他事务可以加 S 锁读，但不能加 X 锁修改。一般写操作前用 FOR UPDATE，读的时候想防止别人改但允许别人读用 LOCK IN SHARE MODE。  

Q10：当前读和快照读的区别？分别靠什么实现？

快照读（普通 SELECT）不加锁，靠 MVCC 实现，读取历史版本，通过 undo log 版本链 + ReadView 判断可见性。

当前读（SELECT...FOR UPDATE、UPDATE、DELETE、INSERT）读取最新版本并加锁，靠行锁/间隙锁/Next-Key Lock 保证并发安全。  

Q11：乐观锁和悲观锁的区别？怎么实现乐观锁？

悲观锁认为并发冲突一定会发生，所以操作前先加锁（数据库行锁就是悲观锁）。乐观锁认为冲突概率低，不加锁，提交时检查版本号/CAS。实现方式：表加 version 字段或 update_time 字段，更新时 WHERE version = 旧值，更新成功则 version+1，失败则重试。适合读多写少、冲突少的场景。
