锁：  
面试题  
第一梯队：必考  
1， InnoDB 有哪些类型的锁？  
答： InnoDB 锁按粒度分：表锁和行锁。行锁按算法分三种：Record Lock（记录锁，锁单条索引记录）、Gap Lock（间隙锁，锁两个索引之间的间隙）、Next-Key Lock（Record + Gap，左开右闭区间，InnoDB 默认）。按模式分：S锁（共享锁，读锁）和X锁（排他锁，写锁）。还有表级的意向锁（IS/IX），是 InnoDB 自动加的，用于快速判断表里有没有行被锁。  
2， 什么是 Next-Key Lock？为什么 InnoDB 默认用它？  
答： Next-Key Lock 是 Record Lock + Gap Lock 的组合，锁定范围是左开右闭区间 (前一条记录, 当前记录]。InnoDB 在 RR 隔离级别下默认使用它，主要解决当前读场景的幻读问题——通过 Gap Lock 锁住间隙，防止其他事务插入新行。唯一索引等值查询命中时会退化为纯 Record Lock，未命中时退化为 Gap Lock。  
3   不同查询条件下，InnoDB 分别加什么锁？  
答： 唯一索引等值查询命中​ → 退化为 Record Lock；未命中​ → 退化为 Gap Lock。

唯一索引范围查询​ → Next-Key Lock，不退化。

非唯一索引等值查询​ → Next-Key Lock + 下一个记录加 Gap Lock。

非唯一索引范围查询​ → Next-Key Lock，不退化。

没走索引的 UPDATE/DELETE​ → 全表聚簇索引每行加 Record Lock，等于锁全表。  

4   死锁产生的四个必要条件是什么？  
答： 互斥，占有且等待，不可强占用，循环等待  
（解释）：① 互斥：资源不能被共享，只能由一个事务持有；

② 占有且等待：事务持有至少一个锁，又在等待获取其他锁；

③ 不可强占用：已分配给事务的锁不能被强制剥夺，只能事务自己释放；

④ 循环等待：多个事务形成头尾相接的循环等待关系。  
  
5 InnoDB 怎么检测和处理死锁？  
答 ： 检测：通过等待图（Wait-For Graph），每次事务请求锁被阻塞时检查是否形成环。  

处理：选择回滚代价最小的事务（按 undo log 量判断）作为牺牲品回滚，抛出 Deadlock found 错误，另一个事务继续执行。应用层需要捕获异常后重试。  
  
6     遇到死锁怎么排查和解决？  
答：  
排查：SHOW ENGINE INNODB STATUS 查看最近一次死锁详情（涉及的事务、SQL、持有的锁、等待的锁）。

解决：最根本的是统一加锁顺序（所有事务按相同顺序获取锁）；其他手段包括缩小事务范围减少锁持有时间、降低隔离级别到 RC 减少 Gap Lock、合理设计索引避免锁全表、应用层加重试机制。  
  
第二梯队：  
Q7：两阶段锁协议是什么？对事务设计有什么影响？

InnoDB 遵循两阶段锁协议：加锁阶段在执行 SQL 时逐个加锁，解锁阶段在事务 COMMIT 或 ROLLBACK 时一次性释放所有锁。影响：事务越晚提交，锁持有时间越长，越容易阻塞其他事务。所以尽量把事务写短、尽快提交，把非数据库操作（RPC、IO）移出事务。  

Q8：为什么说"行锁加在索引上"？没走索引会怎样？

InnoDB 的行锁是加在索引记录上的，不是加在数据行本身。如果 WHERE 条件没走索引（全表扫描），会对每一行聚簇索引记录加 Record Lock，效果等同于锁全表。所以 UPDATE/DELETE 的 WHERE 条件一定要走索引。  

Q9：SELECT ... FOR UPDATE 和 SELECT ... LOCK IN SHARE MODE 的区别？

FOR UPDATE 加 X锁（排他锁），其他事务不能加任何锁也不能修改；LOCK IN SHARE MODE 加 S锁（共享锁），其他事务可以加 S 锁读，但不能加 X 锁修改。一般写操作前用 FOR UPDATE，读的时候想防止别人改但允许别人读用 LOCK IN SHARE MODE。  

Q10：当前读和快照读的区别？分别靠什么实现？

快照读（普通 SELECT）不加锁，靠 MVCC 实现，读取历史版本，通过 undo log 版本链 + ReadView 判断可见性。

当前读（SELECT...FOR UPDATE、UPDATE、DELETE、INSERT）读取最新版本并加锁，靠行锁/间隙锁/Next-Key Lock 保证并发安全。  

Q11：乐观锁和悲观锁的区别？怎么实现乐观锁？

悲观锁认为并发冲突一定会发生，所以操作前先加锁（数据库行锁就是悲观锁）。乐观锁认为冲突概率低，不加锁，提交时检查版本号/CAS。实现方式：表加 version 字段或 update_time 字段，更新时 WHERE version = 旧值，更新成功则 version+1，失败则重试。适合读多写少、冲突少的场景。

Q1：redo log 是干什么的？为什么 MySQL 需要它？WAL 是什么？

redo log 是 InnoDB 引擎层的物理日志，记录的是"对某个数据页的某个偏移量做了什么修改"。它是固定大小、循环写入的（默认两个文件 ib_logfile0/1），写满后覆盖最早的日志。

为什么需要：核心原因是崩溃恢复（crash-safe）和性能。如果没有 redo log，每次事务提交必须直接把脏页刷回磁盘数据文件——随机IO，性能极差。有了 redo log，事务提交只需把修改顺序写入 redo log（顺序IO，极快），然后异步刷脏页。即使崩溃，重启后通过重放 redo log 恢复已提交但未刷盘的数据，保证持久性。

WAL（Write-Ahead Logging）："先写日志，再写数据"的机制。事务提交时必须先写 redo log 并刷盘（fsync），然后才能返回成功。这样即使后续数据页还没刷盘就崩溃，也能从 redo log 恢复。WAL 是数据库保证 ACID 中持久性的基石。  

Q2：binlog 是干什么的？和 redo log 有什么区别？

binlog 是 MySQL Server 层的逻辑日志，记录的是执行的逻辑（如"给 id=2 的行的 age 字段加 10"），以事件形式追加写入，文件会不断滚动生成新文件（不会覆盖旧日志）。

主要用途：主从复制（从库读取 binlog 重放）和按时间点恢复（PITR）。

Q3：为什么需要两阶段提交（2PC）？流程是什么？

为什么需要：redo log 和 binlog 是两个独立的日志系统，如果先写 redo 再写 binlog（或反过来），在写完一个后崩溃，会导致两份日志不一致——主库和从库数据不同步，或者崩溃恢复后数据跟 binlog 对不上。两阶段提交保证两份日志的逻辑一致性。

流程（以 innodb_flush_log_at_trx_commit=1 和 sync_binlog=1 为例）：

Prepare 阶段：事务执行完成后，InnoDB 将 redo log 写入文件并刷盘，标记为 prepare 状态，返回 MySQL Server 层。
Binlog 写入：Server 层将 binlog 写入文件并刷盘。
Commit 阶段：InnoDB 将 redo log 标记为 commit 状态（只需写入内存中的标记，不需要再刷盘）。

崩溃恢复时的判断逻辑：重启后扫描 redo log 中处于 prepare 状态的记录，拿着事务ID去 binlog 里查：

如果 binlog 中能找到该事务（binlog 已写入），则重放 redo log 完成提交（保证主从一致）。
如果 binlog 中找不到该事务（binlog 未写入），则回滚该事务（保证数据不丢但也不多）。  

Q4：undo log 是干什么的？跟 MVCC 什么关系？

undo log 是 InnoDB 引擎层的回滚日志，记录的是数据被修改前的旧版本。主要两个用途：

事务回滚：事务失败时，利用 undo log 将数据恢复到修改前的状态。
MVCC（多版本并发控制）：普通 SELECT 的快照读通过 undo log 构建历史版本链，配合 ReadView 判断可见性，实现读写不互斥。

undo log 分为两类：

insert undo log：插入操作产生的，事务提交后可直接删除（只有本事务可见，不需要给其他事务构建版本链）。
update undo log：更新/删除产生的，需要保留到没有事务需要访问这个版本链时才由 purge 线程清理。  

Q5：MySQL 崩溃重启后，如何保证数据不丢失？完整流程是什么？

崩溃恢复分为三个阶段：

redo log 重放（前滚）：从 checkpoint 位置开始，按顺序重放所有 redo log 记录，将脏页恢复到崩溃前的最新状态。此时包括已提交和未提交事务的修改都恢复了。
binlog 校验：扫描 redo log 中处于 prepare 状态的事务，去 binlog 中确认是否已写入。已写入 binlog 的 prepare 事务需要提交（重放完成），未写入 binlog 的 prepare 事务需要回滚。
undo log 回滚（回滚未提交事务）：对崩溃时处于活跃状态（未提交）的事务，利用 undo log 进行回滚，将数据恢复到修改前的状态。

最终效果：已提交事务的修改一定存在，未提交事务的修改一定不存在，保证 ACID 的持久性和原子性。

Q7：redo log 什么时候刷盘？有哪些参数控制？

redo log 写入路径：用户空间 buffer → 内核缓冲区 → 磁盘文件。

刷盘时机：

事务提交时（由 innodb_flush_log_at_trx_commit 控制）
后台线程每秒刷一次
redo log buffer 使用超过一半时
数据库正常关闭时

关键参数：

innodb_flush_log_at_trx_commit：
1（默认，最安全）：每次事务提交都 fsync 到磁盘
0：每秒写一次，不保证每次提交都刷盘（崩溃可能丢1秒数据）
2：每次提交写到 OS 缓存但不 fsync（崩溃不丢，断电可能丢）

生产环境必须设为 1，保证不丢数据。  

Q8：sync_binlog 参数是什么？怎么配？

控制 binlog 写入 OS 缓存后是否立即 fsync 到磁盘：

0（默认，某些版本）：依赖 OS 刷盘，崩溃可能丢事务
1：每次事务提交都 fsync（最安全，与 redo log 的 innodb_flush_log_at_trx_commit=1 配合实现完整 crash-safe）
N：每 N 个事务 fsync 一次

生产环境推荐设为 1，配合两阶段提交保证数据不丢失。  

Q9：组提交（Group Commit）是什么？解决了什么问题？

问题背景：如果每个事务提交都单独 fsync，高并发下磁盘 IO 会成为瓶颈。

组提交：将多个事务的 redo log / binlog 刷盘操作合并为一次 fsync，减少磁盘 IO 次数，大幅提升吞吐量。

流程：

多个事务进入提交阶段，排队等待
第一个事务触发 fsync，顺便把队列中所有事务的日志一起刷盘
后续事务直接返回成功

InnoDB 有 redo log 组提交和 binlog 组提交，两者配合减少 IO 开销。
