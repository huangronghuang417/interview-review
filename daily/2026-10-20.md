第一梯队：必考（99%会问到）
Q1：Buffer Pool 是干什么的？为什么 MySQL 需要它？

Buffer Pool 是 InnoDB 的内存缓冲池，用于缓存数据页和索引页（默认 128MB，生产环境通常设物理内存的 50%~75%）。

为什么需要：磁盘 IO 是毫秒级，内存是纳秒级，差了几万倍。如果每次读写都直接操作磁盘，数据库根本扛不住并发。Buffer Pool 把热点数据页缓存在内存中，读数据时先查 Buffer Pool（命中就直接返回），写数据时先改 Buffer Pool 中的页（产生脏页），再靠 redo log 和后台线程异步刷盘。所有 SQL 的读写操作都经过 Buffer Pool。

Q2：Buffer Pool 里有哪些链表？各自干什么？

核心三条链表：

Free List（空闲链表）：记录哪些缓存页是空的，需要加载新数据页时从 Free List 取。
LRU List（最近最少使用链表）：管理已被使用的缓存页，按访问热度排序。需要淘汰页时从尾部淘汰。InnoDB 对 LRU 做了优化——分为 young 区（新页区，占 5/8）和 old 区（旧页区，占 3/8），新加载的页先放 old 区头部，只有被再次访问后才晋升到 young 区，防止全表扫描一次性污染整个 Buffer Pool。
Flush List（刷盘链表）：管理所有脏页，按修改时间（LSN）排序，后台线程从 Flush List 尾部取脏页刷盘。
Q3：Change Buffer 是什么？解决了什么问题？

Change Buffer 是 Buffer Pool 中的一块特殊区域，用于缓存非唯一索引上不在 Buffer Pool 中的数据页的 INSERT/UPDATE/DELETE 操作。

解决的问题：如果一条 UPDATE 要修改的非唯一索引页不在 Buffer Pool 中，传统做法必须把索引页从磁盘加载到内存再修改（一次随机 IO）。有了 Change Buffer，可以先不加载索引页，而是把修改操作缓存到 Change Buffer 中，等后续查询需要访问该索引页时再合并（merge）到索引页中。这样把多次随机 IO 合并为一次，大幅减少磁盘 IO，提升写性能。

限制：

只适用于非唯一索引（唯一索引需要立即检查唯一性约束，必须加载索引页）
只缓存不在 Buffer Pool 中的索引页的修改
事务提交时 Change Buffer 的修改会写入 redo log（保证崩溃恢复）
Q4：Log Buffer 是什么？什么时候刷盘？

Log Buffer 是 redo log 的用户空间缓冲区，事务执行过程中产生的 redo log 先写到这里，然后批量写入 OS Cache 和磁盘。

刷盘时机（由 innodb_flush_log_at_trx_commit 控制）：

事务提交时（参数=1 则 fsync 到磁盘）
每秒一次（后台线程）
Log Buffer 使用超过一半时

为什么需要 Log Buffer：如果每次产生一条 redo log 就直接 fsync，高并发下 IO 次数爆炸。Log Buffer 让多个事务的 redo log 可以批量写入，配合组提交（group commit）大幅减少 fsync 次数。

Q5：Buffer Pool 的 LRU 算法和普通 LRU 有什么区别？为什么这么设计？

普通 LRU：新访问的页放头部，满了从尾部淘汰。

InnoDB LRU 的问题：如果执行全表扫描（SELECT * FROM 大表），会把整个 Buffer Pool 的热数据全部挤出去，导致后续正常查询大量缺页，性能骤降。

InnoDB 的改进：把 LRU List 分成两部分：

young 区（新页区）：占 5/8，存放真正的热点数据
old 区（旧页区）：占 3/8，存放新加载但还没被二次访问的页

新页加载策略：数据页首次加载时，放在 old 区的头部，而不是 young 区。只有该页在 old 区被再次访问（且两次访问间隔超过 innodb_old_blocks_time，默认 1 秒），才会晋升到 young 区头部。

效果：全表扫描时，大量页被加载到 old 区头部，但只被访问一次，不会晋升到 young 区，因此不会污染热点数据。扫描结束后这些页自然从 old 区尾部淘汰。

第二梯队：高频（70%+会问）
Q6：脏页是怎么产生的？什么时候刷盘？

产生：事务修改 Buffer Pool 中的数据页后，该页变成脏页（内存与磁盘不一致）。

刷盘时机：

后台线程定期刷（page cleaner thread，每秒/每10秒）
Buffer Pool 内存不足，需要空闲页时淘汰脏页（先刷盘再释放）
redo log 写满，需要覆盖旧日志时强制刷盘（checkpoint 推进）
数据库正常关闭时全量刷盘
Q7：自适应哈希索引（AHI）是什么？

InnoDB 会自动监控某些索引值的访问模式，如果发现某个索引页被频繁等值查询（如 WHERE id = xxx），会在内存中为该索引页建立哈希索引，将 B+ 树查找（O(log n)）优化为哈希查找（O(1)）。

特点：

完全自动，无需人工干预
只适用于等值查询，范围查询无效
只针对热点数据页
可通过 innodb_adaptive_hash_index 关闭（某些高并发场景关闭反而减少锁竞争）
Q8：Sort Buffer 和 Join Buffer 是什么？跟 Buffer Pool 什么关系？

Sort Buffer：每个会话独占的内存区域，用于 ORDER BY 排序操作。如果排序数据量超过 sort_buffer_size，则使用磁盘临时文件做外部排序。

Join Buffer：每个会话独占的内存区域，用于非索引驱动表的 Block Nested-Loop Join。将驱动表的数据批量加载到 Join Buffer，然后跟被驱动表逐行比对，减少磁盘 IO。

跟 Buffer Pool 的关系：Sort Buffer 和 Join Buffer 是会话级内存，不经过 Buffer Pool，由 MySQL Server 层分配。Buffer Pool 是 InnoDB 引擎层的全局共享内存。两者独立。

Q9：如何监控 Buffer Pool 的使用情况？命中率怎么看？
sql
SHOW ENGINE INNODB STATUS;

看 BUFFER POOL AND MEMORY 段：

Buffer pool hit rate：命中率（正常应 > 99%）
Pages read / Pages created / Pages written：读写统计
Youngs/s / Non-youngs/s：young 区/old 区的访问频率

命中率低于 95% 说明 Buffer Pool 太小或全表扫描太频繁。

Q10：Buffer Pool 设置多大合适？太大有什么问题？

建议：物理内存的 50%~75%，专用数据库服务器可以设到 80%。

不能太大：

操作系统需要内存做文件系统缓存（page cache），如果 Buffer Pool 占满所有内存，OS Cache 不足，会影响 binlog、redo log 的写入性能
内存越大，InnoDB 后台线程扫描 LRU/Flush List 的开销越大
极端情况下可能触发 OOM
第三梯队：中频（偶尔会问）
Q11：预读（Read-Ahead）是什么？

InnoDB 会预测接下来可能需要的数据页，提前异步加载到 Buffer Pool 中。

线性预读：顺序扫描超过 innodb_read_ahead_threshold（默认 56）个页时，触发预读下一个 extent（64个页）
随机预读：一个 extent 中有 13 个页被加载到 Buffer Pool 时，触发预读该 extent 剩余页
预读可以减少后续查询的磁盘 IO 等待。
Q12：Doublewrite Buffer 是什么？为什么需要它？

Doublewrite Buffer 是内存中 2MB 的缓冲区 + 磁盘上 2MB 的连续区域（128个页）。

解决的问题：脏页刷盘时，如果写到一半（比如写了 4KB 的页只写了 2KB）发生崩溃，数据页就损坏了。redo log 只能恢复"逻辑修改"，不能修复"页本身损坏"（因为不知道原来的值是什么）。

流程：脏页刷盘时，先写入 Doublewrite Buffer（内存→磁盘连续区域，顺序写），然后再写入真正的数据文件（随机写）。崩溃恢复时，如果数据页损坏，可以从 Doublewrite Buffer 的副本中恢复完整页，再用 redo log 重放修改。
